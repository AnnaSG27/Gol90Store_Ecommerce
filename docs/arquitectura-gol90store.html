Gol90 Store · Arquitectura técnica

Documento HTML de arquitectura, módulos, contenedores, autenticación y features del MVP

Este documento describe el estado real actual de Gol90 Store como stack dockerizado con Django + Django REST Framework + PostgreSQL + Next.js, explicando cómo están conectadas sus piezas, qué features ya funcionan, cuáles están parciales y cómo está implementada la autenticación.

Resumen del sistema

Gol90 Store es una tienda MVP de camisetas de fútbol con arquitectura separada por capas:

  • Frontend: Next.js App Router en frontend_marketplace.
  • Backend: Django + DRF en backend_marketplace.
  • Base de datos: PostgreSQL en contenedor dedicado.
  • Orquestación: Docker Compose con red bridge compartida.

Objetivo del MVP

El proyecto ya no funciona como marketplace de servicios en el flujo principal. Hoy se presenta como tienda de camisetas con:

  • Home visual de tienda.
  • Catálogo conectado a api/productos.
  • Detalle de producto con imágenes y CTA.
  • Login y registro simplificados.
  • Carrito básico en cliente.

Estado actual

Estable Stack dockerizado validado.

Operativo Home, catálogo, detalle, login y carrito responden.

Parcial Carrito sin checkout persistente ni backend propio.

Técnico El backend reporta cambios de modelo en productos aún no migrados.

2. Dockerfiles y arranque

Backend container

  • Base image: python:3.12-slim.
  • Instala dependencias desde requirements.txt.
  • Expone 8000.
  • En Compose no usa el CMD del Dockerfile sino bash /app/entrypoint.sh.

entrypoint.sh hace tres cosas:

  • Espera activamente a PostgreSQL.
  • Ejecuta python manage.py migrate.
  • Ejecuta python manage.py seed_habilidades.
  • Levanta Django con runserver 0.0.0.0:8000.

Frontend container

  • Base image: oven/bun:1-slim.
  • Instala dependencias con bun install --frozen-lockfile.
  • Expone 3000.
  • Arranca con bun run dev.

El frontend se sirve como aplicación de desarrollo, no como build productivo compilado, lo cual simplifica la iteración del MVP.

3. Backend Django: apps, módulos y responsabilidades

App usuarios

Esta app sigue siendo el núcleo de identidad. Conserva parte del modelo histórico, pero hoy el flujo visible solo usa lo mínimo necesario.

  • Usuario: modelo custom con email como identificador.
  • Perfil: one-to-one con Usuario, usado para perfil y compatibilidad.
  • Habilidad: legado del dominio anterior.
  • Experiencia: legado del dominio anterior.

App productos

Esta es la app central del MVP de tienda.

  • Producto: entidad principal del catálogo.
  • ImagenProducto: imágenes asociadas a cada producto.
  • ProductoManager: ofrece query helpers como activos().
  • Serializers: list, detail y create.
  • Views: list/create y detail/update/delete.

4. Modelo de datos del backend

Modelo Producto

  • id: UUID.
  • titulo: nombre comercial del producto.
  • equipo: club o selección.
  • temporada: por ejemplo 2024/25.
  • descripcion: copy del producto.
  • categoria: liga o tipo, con choices.
  • precio: decimal.
  • tallas_disponibles: JSON list.
  • stock: entero positivo.
  • estado: borrador, publicado o agotado.
  • vendedor: FK a Usuario.

Modelo ImagenProducto

  • producto: FK a Producto.
  • imagen: ImageField con upload path por producto.
  • orden: permite ordenar galería.

El backend soporta imágenes reales subidas al servidor, pero el frontend también complementa la demo con imágenes estáticas locales organizadas en public/images/....

5. API REST y protocolos

Protocolos y formatos

  • Frontend ↔ Backend: HTTP/1.1 + JSON.
  • Login JWT: HTTP POST JSON.
  • Creación de producto: multipart/form-data cuando hay imágenes.
  • Backend ↔ DB: protocolo PostgreSQL vía psycopg2.
  • CORS: permitido para http://localhost:3000.

Endpoints activos

Ruta Uso
/api/auth/login/ Entrega access/refresh JWT.
/api/auth/refresh/ Renueva token.
/api/usuarios/registro/ Alta de usuario + perfil.
/api/usuarios/perfil/ Consulta/actualiza perfil autenticado.
/api/productos/ Listado público y POST autenticado.
/api/productos/<uuid:id>/ Detalle público, update/delete autenticado.

6. Cómo funciona la autenticación

Backend auth

  1. El usuario envía email y contraseña a /api/auth/login/.
  2. Simple JWT devuelve access y refresh.
  3. El backend protege rutas con JWTAuthentication.
  4. /api/usuarios/perfil/ requiere Bearer token válido.
  5. Si el usuario no tiene perfil, el backend lo crea automáticamente con tipo cliente.

Frontend auth

  1. authService.login() hace POST a /api/auth/login/.
  2. AuthContext guarda el access_token en localStorage.
  3. Luego consulta /api/usuarios/perfil/ para hidratar el estado del usuario.
  4. Las rutas bajo src/app/(protected) verifican token y redirigen a /login si falta.
  5. logout() limpia token y perfil local.
La autenticación hoy es suficiente para el MVP, pero el frontend no implementa aún refresh automático del access token ni invalidación centralizada por expiración.

8. Cómo funciona el catálogo en frontend

Carga de datos

  1. ServicesExplorer usa el hook usePublicaciones().
  2. Ese hook llama a getPublicaciones() en publicacionService.ts.
  3. El service construye query params y consume /api/productos/.
  4. El backend devuelve paginación DRF estándar: count, next, previous, results.
  5. Los datos se adaptan a props visuales mediante adapters.ts.

Filtros y búsqueda

  • Búsqueda: backend, por titulo, equipo y temporada.
  • Categoría: backend.
  • Precio: backend, vía precio_min y precio_max.
  • Ordenamiento: backend.
  • Equipo / talla / temporada: frontend, sobre resultados ya obtenidos.

Eso significa que hoy el filtro híbrido funciona bien para demo, aunque no toda la lógica de filtrado reside aún en la API.

9. Cómo funciona el detalle de producto

Flujo técnico

  1. La ruta /productos/[id] renderiza ServiceDetail.
  2. usePublicacion(id) llama a GET /api/productos/<id>/.
  3. toServiceDetailProps() normaliza el DTO del backend.
  4. La vista compone galería, descripción, bloque de tienda y pricing card.

Imágenes en el detalle

El backend devuelve imagen_principal_url e imagenes[], pero los productos demo actuales no traen imágenes subidas. Para no dejar el detalle vacío, el frontend implementa un fallback en catalog-assets.ts:

  • Si hay imágenes del backend, las usa.
  • Si no hay imágenes, asigna imágenes locales desde public/images/productos.
  • Así el detalle y el catálogo siempre se ven completos en la demo.

10. Cómo funciona el carrito

Implementación

El carrito está implementado completamente en frontend dentro de src/features/cart/CartContext.tsx.

  • Estado global con React Context.
  • Persistencia en localStorage.
  • Agregar producto desde el detalle.
  • Soporte para talla seleccionada.
  • Ajuste de cantidad.
  • Cálculo de subtotal.

Limitaciones actuales

  • No existe tabla de carrito en backend.
  • No existe checkout.
  • No existe reserva real de stock.
  • No existe orden o pago.

Parcial Es un feature de demo, no un flujo transaccional final.

13. Features parciales o heredados

Parcialmente implementado

  • Carrito: solo en frontend, sin checkout ni órdenes.
  • Imágenes de producto: backend las soporta, pero la demo actual se apoya mucho en assets locales.
  • Filtros avanzados: equipo, talla y temporada aún no están resueltos completamente del lado API.
  • Perfil: existe, pero está simplificado para no dominar la experiencia.

Heredado pero fuera del flujo principal

  • Habilidades: permanecen en backend por compatibilidad.
  • Experiencias: permanecen en backend por compatibilidad.
  • Contracts / Dashboard / Services legacy: las rutas visibles fueron redirigidas o neutralizadas.
  • Tipo de usuario: sigue existiendo en backend, pero ya no se expone en la superficie principal.

14. Riesgos y deuda técnica actual

Deuda visible

  • La feature services todavía conserva nombres internos heredados aunque su semántica visible ya es de productos.
  • El componente FreelancerProfileCard ya no habla de freelancer, pero el nombre interno sigue legado.
  • El tipo TipoUsuario sigue declarando valores del dominio antiguo.

Deuda operativa

  • El backend avisa que hay cambios en productos sin migración aplicada.
  • El entrypoint sigue ejecutando seed_habilidades, que ya no es relevante para el flujo principal.
  • El frontend usa NEXT_PUBLIC_API_URL=http://localhost:8000, correcto para desarrollo local, no para despliegue público.

15. Conclusión técnica

Gol90 Store ya tiene una arquitectura MVP consistente: frontend y backend están desacoplados por REST, la autenticación está resuelta con JWT, la orquestación está contenida en Docker Compose y el catálogo ya opera sobre una entidad real Producto.

El sistema ya funciona como tienda demo de camisetas. Lo que sigue ya no es una reestructuración grande, sino evolución incremental: checkout, persistencia real del carrito, imágenes por producto desde backend, depuración de legado interno y pulido comercial.
