# 06 — Commit and Repository Rules

## Commit Style

Use Conventional Commits in clear, beginner-friendly English.

Allowed common types:

```text
feat
fix
test
docs
chore
ci
refactor
style
```

Examples:

```text
feat: add marketplace order models
feat: implement simulated checkout flow
fix: restrict sellers to their own products
test: add checkout and inventory tests
docs: add sprint 2 testing strategy
ci: run backend tests on pull requests
chore: clean contributor metadata
```

## Strictly Forbidden in Commits

Do not include any of the following in commit messages, commit bodies, or commit trailers:

```text
Co-authored-by
codex
claude
cursor
ai
ai-generated
generated by
bot
assistant
```

Exception: normal words that appear inside code or package names should not be changed blindly. The rule is specifically about attribution, commits, and generated metadata.

## Commit Scope

Each commit must represent one coherent change.

Good:

```text
feat: add order models and migrations
test: add order creation tests
fix: enforce seller order permissions
```

Bad:

```text
feat: add everything
update project
final sprint 2
changes
```

## Recommended Commit Sequence

Use this as a guide, not as a fake history.

```text
docs: add sprint 2 development specifications
chore: stabilize project baseline and clean contributor metadata
feat: add marketplace order and payment models
feat: implement checkout inventory and order management api
test: add automated tests for checkout orders inventory and permissions
feat: connect cart checkout and buyer order history
feat: add seller dashboard for products inventory and orders
fix: harden authentication state for protected marketplace flows
ci: add automated checks for backend quality and tests
docs: update sprint 2 development evidence and run instructions
```

Do not create a commit unless the work described by the message was actually done.

## Branching Recommendation

Recommended branch flow:

```text
develop
feature/sprint2-specs
feature/sprint2-backend-orders
feature/sprint2-frontend-orders
feature/sprint2-tests-ci
docs/sprint2-wiki-evidence
```

If time is short, use fewer branches:

```text
develop
feature/sprint2-mvp-v2
docs/sprint2-evidence
```

Do not work directly on `main` unless required by the course workflow.

## Pull Request Expectations

Each PR should include:

- Summary of changes.
- Related issue or Sprint 2 scope item.
- Commands run.
- Test results.
- Known limitations.

Do not claim tests passed unless they were actually run.

## Contributor Cleanup

Search case-insensitively for:

```text
Felipe
Tomás
Tomas
```

Replace incorrect authorship references with the valid contributor list:

```text
Andres Velez Rendon
Anna
David Curelop
Abraham
```

Record the command used and post-cleanup search result in development evidence.

## File Hygiene

Do not commit:

- local `.env` files with secrets
- database dumps with sensitive data
- node_modules
- Python caches
- coverage HTML output unless intentionally required
- editor-specific noise
- generated files not needed by the project

## Documentation Honesty

Documentation must match actual code.

Do not write:

- "implemented" for pending work
- "tests passing" without a real test run
- "deployed" unless deployed
- "coverage achieved" without coverage command output

Use honest status terms:

```text
Implemented
Partially implemented
Deferred
Blocked
Not executed
Pending validation
```
